# LM4 Cine Meter

Офлайн-приложение для Opple Light Master 4 (спектрометр/люксметр/цветомер) под
кинооператоров. Отдельный, самостоятельный проект — не форк и не часть другого
приложения этого же владельца репозитория (TAKE:ONE), живёт только в этой ветке
(`lm4`), обратно в `dev`/`main` никогда не мержится.

## Зачем

Официальное приложение Opple не устраивает: перегружено параметрами, требует
аккаунт/интернет, не заточено под то, как реально работает кинооператор на
площадке. Нужно минималистичное, полностью офлайн (кроме самого BLE, который по
своей природе локальный) приложение под конкретный рабочий процесс:

1. Два экрана измерений — **Камера** (ISO, выдержка, диафрагма) и **Свет**
   (цветовая температура, зелень/пурпур, CRI, R9).
2. **Камера** — работает как экспонометр: рекомендация по диафрагме и по
   ND-фильтру.
3. **Свет** — рекомендация по фильтрации зелени (конкретный светофильтр на
   прибор/источник).
4. Полностью офлайн, без обязательной регистрации.
5. Максимальная практическая точность с осознанными допущениями — это не
   Sekonic, заказчик это понимает и принимает.

## Файлы и деплой

- `index.html` — вся страница (HTML/CSS/JS в одном файле, без сборки, без
  внешних зависимостей на фронте).
- `server.js` — 6-строчный статик-сервер (`express.static` с
  `extensions:['html']`), отдаёт `index.html` на `/`.
- `package.json` — единственная зависимость `express`.
- Отдельный сервис на Railway, отслеживает эту ветку, автодеплой включён.
- **Web Bluetooth требует https (или localhost)** — поэтому страница живёт на
  публичном домене, просто открыть файл с телефона напрямую не сработает.

## Текущий статус

Протокол BLE прибора реверс-инженерен вручную и закрыт (была главная
неизвестная в проекте). Собран рабочий прототип с тремя вкладками — Камера,
Свет, Калибровка; последняя реально подключается к прибору по Web Bluetooth и
читает с него данные. **Главное нерешённое** — перевод сырых показаний сенсора
в точные Lux/CCT/Duv/CRI/R9: для этого собирается калибровочный датасет,
которого пока недостаточно (см. "Состояние калибровки" ниже).

## Разобранный протокол устройства

Кастомный GATT-сервис в стиле Nordic UART, UUID `6e400001-b5a3-f393-e0a9-e50e24dcca9e`.
Одна характеристика `6e400003-b5a3-f393-e0a9-e50e24dcca9e` используется и на
запись команд (write без ответа), и на notify для ответов — не разделены на
приём/передачу. Подключение без сопряжения/пина.

**Обнаружение устройства**: прибор НЕ публикует этот сервис в рекламном BLE-
пакете (том, что виден при сканировании до коннекта) — сервис виден только
после подключения, в полном списке GATT-сервисов. Поэтому искать устройство
нужно по имени (`LMaster...`), а не по фильтру сервиса — иначе браузер вообще
не покажет прибор в списке.

**Формат кадров** (общий для команд и ответов, с фрагментацией на BLE-пакеты):
первый байт — тип фрагмента в старших 3 битах (`0x00` — одиночное сообщение
целиком, `0x80` — первый фрагмент + 2 байта big-endian заявленной общей длины,
`0xA0|номер` — средний фрагмент, `0xC0|номер` — последний). Полезная нагрузка
склеивается из всех фрагментов подряд.

Команда: `[0, 0x13, 0, 0, seqno, 0, длина_доп_данных, 0, 0, опкод_старший_байт, опкод_младший_байт, ...доп_данные]`,
обёрнутая в ту же схему фрагментации. Код ответа — байты 9-10 собранного
сообщения (big-endian).

**Опкоды**:
- `2560` (запрос замера) → ответ `2561`
- `2564` (запрос заводской калибровки) → ответ `2565`
- `2566` → ответ `2567` (11 байт полезной нагрузки) — **смысл не расшифрован**,
  не факт что вообще нужен. Кандидат на "готовое значение CRI/R9 с самого
  прибора" (см. ниже).
- `2562`, `2568` — опробованы, прибор не ответил.

**Ответ на замер (2561), 23 байта**: 10 знаковых 16-битных little-endian чисел
(сырые отсчёты 10 каналов сенсора AS7341: предположительно F1..F8 —
415/445/480/515/555/590/630/680 нм — плюс Clear и NIR, порядок каналов не
проверен на 100%, принят как логичный), затем 2 байта `power`, затем 1 байт
`C0`.

**Ответ на калибровку (2565)**: 1 служебный байт, затем 11 float32 little-
endian чисел — заводские поканальные калибровочные коэффициенты (все около
1.0). Число 11 совпадает с офиц. названием чипа AS7341 — "11-Channel Spectral
Color Sensor" (8 полос F1-F8 + Clear + NIR + отдельный канал Flicker) — то
есть калибровка покрывает на один канал больше, чем пакет замера; вероятно,
Flicker читается отдельной командой (в LM3 было отдельное измерение
мерцания) — для LM4 не проверялось.

**`power`**: несмотря на название, почти не меняется (~3100-3300) даже при
разнице освещённости в 46 раз — не яркость, скорее телеметрия заряда батареи
(в LM3 аналогичное поле шло в таблицу перевода в % заряда). Для фотометрии не
нужно, годится только для индикатора батареи в UI. **`C0`** тоже почти не
меняется независимо от яркости — предположительно температура платы, тоже не
про свет.

Хорошая новость: раз ни `power`, ни `C0` не выдают состояние авто-экспозиции
сенсора (усиление/время интегрирования), похоже, прибор в этом режиме замера
работает на фиксированных настройках — сырые каналы должны более-менее прямо
(без скрытой компенсации) соотноситься с реальной яркостью, что упрощает
калибровку.

## Прототип — три вкладки

**Камера** — классическая формула падающего света ISO 2720
(`Ev = log2(Lux·ISO/C)`, `N = sqrt(t·2^Ev)`), калибровочная константа `C` по
умолчанию 250, предполагается подстраивать не по эталонному прибору, а по
реальным отснятым кадрам. Считает нужную плотность ND-фильтра под желаемую
диафрагму и подбирает ближайший стандартный номинал (ND2...ND1000).

**Свет** — по введённому Duv рекомендует конкретный фильтр из линейки Rosco
Cinegel Minus/Plus Green (шкала подтверждена по официальному прайсу Rosco:
Full = CC30, 3/4 = CC22.5, 1/2 = CC15, 1/4 = CC07.5, 1/8 = CC03.5). Перевод
Duv → CC-шкала пока через приблизительный коэффициент (единицы разные по
физическому смыслу, точной публичной таблицы не нашлось) — помечен в коде как
требующий полевой калибровки. Также качественная оценка CRI Ra и R9 с
пояснениями (низкий R9 — плохо переданная кожа/красные в кадре).

**Калибровка** — рабочий (не заглушка) Web Bluetooth клиент: подключение к
прибору по имени, автоматическое чтение заводских коэффициентов при коннекте,
кнопка "Замер" показывает сырые каналы, поля для ручного ввода того, что
одновременно показывает официальное приложение Opple (Lux, CCT, x, y, CRI,
R9), кнопка сохраняет пару в localStorage, кнопка экспорта выгружает всё в
JSON. Это инструмент сбора калибровочного датасета, не законченная фича —
своей матрицы пересчёта в CCT/CRI внутри пока нет.

## Состояние калибровки

Собрано 4 точки (сырые данные + то, что показало официальное приложение для
того же источника в тот же момент). 3 из них похожи по цветовой температуре
(тёплые, 2977-3984K) — по ним пробовалась грубая линейная модель (3
объединённых диапазона каналов → XYZ), идеально легла на эти же 3 точки (что
математически неизбежно и ничего не доказывает — 3 точки на 3 неизвестных
решаются точно всегда), но провалилась на 4-й, контрольной точке — холодный
дневной свет 6489K: предсказанный Lux разошёлся с реальным ~в 1.5 раза,
предсказанная цветность — совсем другая часть цветового пространства (тёплая
вместо холодной).

**Вывод**: нужен полноценный датасет, 15-30+ точек, с разнообразием по трём
осям одновременно:
- цветовая температура (от свечи ~1800K до дневного света 6500K+),
- сдвиг по зелени/пурпуру отдельно от температуры (специально нужны источники,
  которые заведомо "кривят" — офисный люминесцентный свет, дешёвые LED-ленты,
  старые энергосберегайки, а не только чистые лампы накаливания/дневной свет,
  которые почти не отклоняются от линии чёрного тела),
- яркость (один и тот же источник на разном расстоянии).

Сбор идёт постепенно, через вкладку "Калибровка", по мере того как заказчик
встречает подходящие источники света.

## Нерешённая проблема: CRI и R9

Честный расчёт по документации AS7341 (ams OSRAM) требует восстановления
полного спектра источника (380-1000 нм) по показаниям каналов через отдельную
калибровочную матрицу спектральной реконструкции — обычно получается съёмкой
набора эталонных цветовых мишеней настоящим спектрометром/монохроматором,
чего физически нет и не будет. Два пути:

(а) обучить приблизительную регрессию прямо на показаниях CRI/R9 самого
официального приложения Opple (как псевдо-эталон) — менее строго физически
обоснованно, чем честная спектральная реконструкция, но реалистично
достижимо;

(б) проверить, не отдаёт ли прошивка уже готовое значение CRI/R9 через
необъяснённый опкод `2566`/`2567` (11 байт, смысл не расшифрован) — открытый
вопрос, не проверено.

## Источник и лицензия

Отправная точка для понимания протокола — открытый проект
`github.com/OlliV/open-light-master` (GPL-3.0), реверс-инженеренное веб-
приложение для предыдущей модели, Light Master 3. Другой сенсор (6 каналов
AS7262 против 10-11 каналов AS7341 у LM4) и другой порядок байт (big-endian
против little-endian у LM4), но архитектура транспорта, схема фрагментации и
нумерация опкодов совпали почти один в один — дало быстрый старт при реверсе
LM4. Готовая цветовая математика оттуда (XYZ → CCT/Duv/Tint по формулам CIE)
напрямую переиспользуема, как только появится надёжный XYZ.

## Что дальше

1. Продолжать копить калибровочные точки через вкладку "Калибровка" —
   целенаправленно закрывая пробелы по цветовой температуре, зелени и
   яркости, а не просто увеличивая счётчик.
2. Когда наберётся достаточно точек — посчитать регрессию сырые каналы → XYZ
   (вероятно с регуляризацией, точек всё равно будет меньше, чем хотелось бы
   для полностью свободной 10-параметровой модели на канал).
3. Разобраться с CRI/R9 — регрессия на показаниях официального приложения,
   либо проверить гипотезу про готовое значение с прибора (опкод 2566/2567).
4. Откалибровать константу Duv→CC для зелёных фильтров по факту (реальный
   фильтр известного номинала + сверка показаний).
5. Подключить живые данные с прибора (вкладка "Калибровка") к вкладкам
   "Камера" и "Свет" вместо ручного ввода, когда модель пересчёта станет
   достаточно надёжной.
